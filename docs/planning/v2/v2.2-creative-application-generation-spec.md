# V2.2 Creative Application Generation Spec

Status: draft
Source: Manual QA screenshots in `docs/testing/manual-QA-result` and local model comparison notes from 2026-05-16.

## Problem Statement

The current application generation workflow is too narrow. Manual QA showed that the generated cover letter repeated a small number of accepted evidence matches, leaned heavily on one `Job application assistant` profile fact, and failed to use the broader CV story: education, business background, integrations, Salesforce, AI tooling, architecture, languages, location, and transferable competencies.

This is not only a model-quality problem. The same or similar local model can produce richer output when given the CV, asked to extract skills and competencies, and then given the job opening. The app currently strips that context down too aggressively before draft generation.

The current workflow treats approved evidence matches as the main creative input. That is useful for claim safety, but too restrictive for persuasive writing. V2.2 should make the app generate from a richer candidate/job strategy while preserving the existing trust boundary through evidence approval and claim audit.

## Goals

- Generate cover letters and short motivations that feel specific, human, and persuasive.
- Use the full approved profile, not only matched evidence snippets, when forming candidate fit and strategy context.
- Extract and use competencies, transferable strengths, and narrative themes from CV/profile facts.
- Keep concrete experience claims auditable against approved evidence.
- Reduce weak or over-broad evidence matches that cause repetitive drafts.
- Preserve local AI support, including smaller models, by shaping context clearly before asking for final prose.
- Keep the user in control of trust-sensitive approval decisions.

## Non-Goals

- No automatic job submission.
- No claim generation from unapproved imported CV facts.
- No requirement to store raw full CV text as permanent generation context.
- No full rewrite of the profile fact model unless a field is clearly needed.
- No removal of evidence matching or claim audit.
- No dependence on a cloud-only model.

## Diagnosis

Manual QA exposed three linked issues.

First, profile import and approval can leave the profile too thin or too coarse. If one broad project fact is approved and other facts are missing, evidence matching stretches that one fact across many job requirements.

Second, evidence matching currently has no explicit quality bar. A weak lexical overlap can become an approved-looking match. When the user accepts many of those matches, generation receives a repetitive evidence set.

Third, draft generation receives only approved evidence, unmatched requirements, gap decisions, custom facts, and basic application metadata. It does not receive a broader candidate summary, grouped skills, competency extraction, education context, career context, or application strategy.

The model therefore behaves like a checklist writer. It repeats what it was given because the app has already removed the richer context that would let it synthesize.

## Product Direction

V2.2 adds a strategy layer between profile evidence and final draft generation.

The workflow should become:

```text
Approved profile facts
+ job posting
=> job analysis
=> candidate fit brief
=> evidence matching with quality labels
=> user evidence/gap review
=> application strategy
=> creative draft generation
=> claim audit
=> user edit/export
```

The candidate fit brief and application strategy are not proof by themselves. They are writing context. Concrete claims in the final draft still need support from per-application approved evidence or approved job-local custom facts. A profile fact can support a final concrete claim only after it has been selected into approved evidence for that application. Gap decisions can shape cautious wording, but they never become proof.

## Canonical Terms

**Candidate Fit Brief**
A generated, structured summary of the candidate's relevant skills, competencies, projects, education, work history, language strengths, transferable experience, and likely job-fit themes for one application.

**Application Strategy**
A generated writing plan for one application. It chooses the strongest story angles, what to emphasize, what to avoid, how to handle gaps, and which evidence should support each theme.

**Evidence Quality**
A classification for an evidence match that helps prevent weak matches from being treated like strong proof.

Suggested values:

```text
Strong
Partial
Weak
```

**Writing Context**
Context the model may use to shape tone, structure, and emphasis, but not as standalone proof for concrete claims.

**Proof Context**
Per-application approved evidence matches and approved job-local custom facts that can support concrete claims. Approved profile facts are source material for matching and fit-brief generation, but they are not final proof until selected into approved evidence for the current application.

## Workflow Changes

### 1. Profile Import Should Extract Competencies

V2.1 import should be extended or followed up so it extracts more than technical skills.

The import should extract:

- technical skills and tools
- programming languages, frameworks, databases, cloud, DevOps, AI tools
- architecture and integration competencies
- project evidence
- work history and responsibilities
- business, customer, stakeholder, and communication competencies
- education and study themes
- languages
- domains and sectors
- transferable strengths
- allowed claims
- forbidden or risky claims

The prompt should no longer prefer only `1-5` high-signal facts for a full CV. That can be too little for a useful evidence library. Prefer a richer set of reviewable draft facts grouped by type or theme.

### 2. Add Candidate Fit Brief Generation

Add an AI operation that receives:

- selected application metadata
- job posting or job signals
- all approved profile facts
- optionally approved job-local custom facts
- selected language and tone preference

It returns strict JSON:

```json
{
  "candidateSummary": "string",
  "skillGroups": [
    {
      "name": "string",
      "items": ["string"],
      "supportingProfileFactIds": ["guid"]
    }
  ],
  "competencies": [
    {
      "name": "string",
      "summary": "string",
      "supportingProfileFactIds": ["guid"]
    }
  ],
  "relevantProjects": [
    {
      "title": "string",
      "whyRelevant": "string",
      "supportingProfileFactIds": ["guid"]
    }
  ],
  "transferableStrengths": [
    {
      "name": "string",
      "summary": "string",
      "supportingProfileFactIds": ["guid"]
    }
  ],
  "riskNotes": ["string"]
}
```

Every concrete item should reference supporting approved profile facts for traceability. These references make the fit brief explainable, but they do not bypass evidence review. If a useful theme is only an interest or weak fit, it should appear in `riskNotes` or be marked cautiously in the summary.

### 3. Improve Evidence Matching

Evidence matching should compare each job signal against the full approved profile and candidate fit brief.

The matcher should return:

```json
{
  "evidenceMatches": [
    {
      "signalId": "existing-job-signal-id",
      "profileFactId": "approved-profile-fact-guid",
      "quality": "Strong|Partial|Weak",
      "summary": "short evidence summary grounded only in the approved fact",
      "matchedTerms": ["string"],
      "reason": "why this fact supports the signal"
    }
  ],
  "unmatchedRequirements": [
    {
      "signalId": "existing-job-signal-id",
      "recommendation": "honest gap-handling recommendation"
    }
  ]
}
```

Rules:

- Approved strong matches can support direct claims.
- Approved partial matches can support careful claims with narrower wording.
- Weak matches should be shown to the user as questionable and should not be auto-approved.
- Weak matches should not support direct experience claims. If the user keeps a weak match, generation should treat it as cautious writing context unless the user replaces it with stronger evidence or an approved custom fact.
- Unsupported signals become unmatched requirements.
- Avoid matching many unrelated signals to the same broad profile fact unless the fact genuinely supports each signal.
- Prefer semantic support over keyword overlap.

### 4. Add Application Strategy Generation

After evidence and gaps are reviewed, generate an application strategy before the final draft.

Inputs:

- job analysis
- candidate fit brief
- approved evidence
- evidence quality
- unmatched requirements
- gap decisions
- approved custom facts
- selected language
- tone preference

Output:

```json
{
  "primaryAngles": [
    {
      "title": "string",
      "message": "string",
      "evidenceIds": ["approved-evidence-id"],
      "profileFactIds": ["guid"]
    }
  ],
  "secondaryAngles": [
    {
      "title": "string",
      "message": "string",
      "evidenceIds": ["approved-evidence-id"],
      "profileFactIds": ["guid"]
    }
  ],
  "gapHandling": [
    {
      "requirementId": "string",
      "approach": "Ignore|MentionAsLearningInterest|CoveredByCustomFact",
      "wordingGuidance": "string"
    }
  ],
  "avoidClaims": ["string"],
  "toneGuidance": "string",
  "draftOutline": ["string"]
}
```

The strategy should explicitly choose what not to cover. A strong cover letter should not mechanically mention every job requirement. Strategy `profileFactIds` are traceability/context references; concrete claims require `evidenceIds` or approved custom facts.

### 5. Rewrite Draft Generation Prompt

Draft generation should receive the application strategy and candidate fit brief in addition to approved evidence.

Rules:

- Write naturally for the selected language.
- Use the job opening's tone, but do not copy large phrases from it.
- Prefer 2-3 strong story angles over exhaustive requirement coverage.
- Use approved evidence and approved custom facts for concrete experience claims.
- Use candidate fit brief as writing context only. Fit brief profile fact ids explain where a theme came from, but they do not independently authorize a final concrete claim.
- Mention gaps only according to gap decisions.
- Avoid repeating the same profile fact in multiple paragraphs unless it is the central story.
- Include transferable experience where relevant and supported.
- Avoid generic claims such as "I am very interested" unless grounded in a concrete reason.
- Short motivation should be a concise value proposition, not a compressed copy of the cover letter.

### 6. Keep Claim Audit as the Safety Net

Claim audit remains required after generation and after user edits.

The audit should receive:

- final cover letter
- final short motivation
- approved evidence
- candidate fit brief support mappings
- approved custom facts
- gap decisions

Audit rules should distinguish:

- supported concrete claims with per-application approved evidence or approved job-local custom facts
- cautious motivation/interest statements
- unsupported experience claims
- broad soft-skill claims that need per-application approved evidence or cautious non-evidentiary wording

## Backend Changes

Add AI provider methods:

```csharp
Task<CandidateFitBriefResult> GenerateCandidateFitBriefAsync(CandidateFitBriefInput input, CancellationToken ct);
Task<ApplicationStrategyResult> GenerateApplicationStrategyAsync(ApplicationStrategyInput input, CancellationToken ct);
```

Update or extend:

```csharp
Task<EvidenceMatchResult> MatchEvidenceAsync(EvidenceMatchInput input, CancellationToken ct);
Task<DraftGenerationResult> GenerateDraftAsync(DraftGenerationInput input, CancellationToken ct);
Task<ClaimAuditResult> AuditClaimsAsync(ClaimAuditInput input, CancellationToken ct);
```

Likely persistence additions on `JobApplication`:

```text
CandidateFitBrief json nullable
ApplicationStrategy json nullable
```

If persistence is kept lean, these may initially be stored as workflow artifacts on the application, similar to `JobSignals`, `EvidenceMatches`, and `UnmatchedRequirements`.

Update AI run records so each step is visible:

```text
CandidateFitBrief
JobAnalysis
EvidenceMatching
ApplicationStrategy
DraftGeneration
ClaimAudit
```

`Prepare application` should run job analysis, candidate fit brief generation, and evidence matching. It should still stop at evidence review.

`Generate and audit draft` should run application strategy, draft generation, and claim audit. It should stop at draft review.

## Frontend Changes

### Application Detail

Show a compact candidate fit summary after preparation:

- candidate summary
- strongest relevant skill groups
- strongest competencies
- relevant projects
- risk notes

Show evidence quality during review:

- Strong matches are easy to approve.
- Partial matches are visible as careful-use evidence.
- Weak matches require deliberate user decision: remove them, replace them with stronger evidence/custom facts, or keep them as cautious context only.
- Unmatched requirements remain in the gap handling flow.

Show the generated application strategy before or beside the draft:

- primary angles
- gaps to mention or avoid
- claims to avoid
- tone guidance

The user does not need to edit strategy in V2.2, but they should be able to understand why the draft took its shape.

### Profile

Profile import/review should make competency extraction visible:

- skills
- projects
- competencies
- work/education facts
- transferable strengths
- allowed claims

The review flow should encourage approving enough useful facts before starting real applications.

## Prompt Changes

Add prompts:

```text
candidate-fit-brief.md
application-strategy.md
```

Revise prompts:

```text
assisted-profile-import.md
evidence-matching.md
draft-generation.md
claim-audit.md
```

Prompt design principles:

- Separate extraction, strategy, writing, and audit.
- Ask smaller local models for structured intermediate reasoning before final prose.
- Make the final draft prompt less legalistic than the audit prompt.
- Keep strict JSON for machine steps.
- Keep final prose output as JSON fields only, but allow creative, natural language inside those fields.

## Testing Decisions

Backend tests should cover:

- candidate fit brief generation stores structured workflow context
- evidence matching quality labels are validated
- weak matches are not silently treated as strong evidence
- strategy generation uses approved evidence and gap decisions
- draft generation receives strategy and fit brief
- claim audit still flags unsupported claims
- provider failure preserves prior stable state
- malformed JSON fails gracefully with repair where appropriate
- fake provider returns deterministic V2.2 artifacts

Frontend tests should cover:

- fit brief appears after preparation
- evidence quality labels are visible
- weak evidence requires deliberate review
- strategy summary appears before or with draft review
- edited drafts mark audit stale as before

Manual QA should compare:

- app-generated output against a direct chat baseline using the same model
- broad CV/job fit coverage
- repetition level
- use of transferable competencies
- unsupported claim audit behavior

## Acceptance Criteria

- A CV with rich technical and non-technical experience produces multiple reviewable profile facts and competencies.
- Preparing an application creates a candidate fit brief that reflects the broader approved profile.
- Evidence matches include quality labels and avoid stretching one broad fact across unrelated job signals.
- Draft generation uses 2-3 coherent story angles instead of listing accepted skills.
- The Vejle Kommune AI-builder example produces a draft that can mention AI/local tooling, integrations, education, business/customer experience, communication, and location where supported.
- The generated short motivation is a distinct concise pitch.
- Concrete claims remain auditable against approved evidence or approved custom facts.
- Unsupported or over-broad claims are caught by claim audit.
- The app's output is meaningfully closer to the direct-chat baseline when using the same local model.

## Open Questions

1. Should candidate fit brief generation happen automatically after any profile import approval?
   Recommended answer: no for V2.2. Generate it per application because relevance depends on the job.

2. Should the user edit the application strategy?
   Recommended answer: not initially. Show it for transparency first; add editing later if manual QA shows it helps.

3. Should full approved profile facts be sent to draft generation?
   Recommended answer: preferably no as raw proof. Send the candidate fit brief and strategy as structured writing context, and send approved evidence/custom facts as proof context. If full approved profile facts are included for context-window reasons, prompts and validation must state that they cannot support final concrete claims unless selected into approved evidence.

4. Should weak evidence ever support claims?
   Recommended answer: not direct experience claims. A weak kept match may guide cautious wording, but direct claims should require strong or partial approved evidence, or an approved custom fact.

5. Should V2.2 change the default model?
   Recommended answer: no. Improve context shaping first. Model choice can still be documented as a quality lever.
