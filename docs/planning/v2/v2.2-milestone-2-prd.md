# V2.2 Milestone 2 Product Requirements Document

Status: done
Source: docs/planning/v2/v2.2-creative-application-generation-spec.md

## Goal

Improve evidence review quality and add an application strategy step, so generation can choose strong story angles instead of mechanically repeating accepted matches.

## Problem Statement

Milestone 1 creates richer candidate context, but draft generation will still be weak if evidence matching treats every lexical overlap as usable proof. Manual QA showed one broad profile fact matched against many job signals, causing a repetitive and narrow cover letter.

The app needs to distinguish strong evidence from partial or weak evidence, and it needs a writing strategy that decides which themes to emphasize, which gaps to handle cautiously, and which claims to avoid.

## Solution

Milestone 2 adds evidence quality labels and application strategy generation.

Evidence matching should classify matches as `Strong`, `Partial`, or `Weak`, and unsupported signals should remain unmatched. Weak matches are opt-in only: they must not be preselected, auto-approved, or visually equal to `Strong` or `Partial` matches. The frontend should make weak matches visibly questionable and require deliberate user review.

After evidence and gaps are reviewed, the app should generate an `ApplicationStrategy`. It must not be generated during `Prepare application`. The strategy chooses 2-3 primary story angles, secondary angles, gap-handling guidance, claims to avoid, tone guidance, and a draft outline. It uses the candidate fit brief, approved evidence, evidence quality, unmatched requirements, gap decisions, and approved custom facts. Candidate fit brief references can shape narrative, but strategy items need approved evidence or approved custom facts before they become concrete final-draft claims.

## User Stories

1. As a job applicant, I want evidence matches to show their strength, so that I do not approve weak proof by accident.
2. As a job applicant, I want weak matches to be visually different from strong matches, so that I know where judgment is needed.
3. As a job applicant, I want partial matches to guide careful wording, so that the draft does not overstate my experience.
4. As a job applicant, I want unsupported job signals to remain unmatched, so that the app does not force a false fit.
5. As a job applicant, I want the app to avoid matching many unrelated requirements to one broad profile fact, so that generated text does not become repetitive.
6. As a job applicant, I want the app to plan the cover letter before writing it, so that the final draft has a coherent story.
7. As a job applicant, I want the strategy to choose what not to cover, so that the letter does not read like a checklist.
8. As a job applicant, I want strategy gaps to follow my gap decisions, so that learning interests and ignored requirements are handled honestly.
9. As a job applicant, I want claims to avoid listed before generation, so that risky wording is visible.
10. As a developer, I want evidence quality validated in the backend, so that providers cannot return unknown quality values.
11. As a developer, I want strategy generation to use approved evidence and fit brief context, so that draft generation has both proof and narrative direction.
12. As a developer, I want application strategy stored as latest workflow state, so that draft generation and audits can be reproduced from persisted context.

## Implementation Decisions

- Extend evidence matching output with `quality` and `reason`.
- Support evidence quality values: `Strong`, `Partial`, and `Weak`.
- Treat unsupported signals as unmatched requirements rather than weak evidence.
- Validate quality values and reject malformed provider output.
- Update evidence review UI to show quality labels and reasons.
- Make weak evidence opt-in only. Weak matches must not be preselected, auto-approved, or visually equivalent to `Strong` or `Partial` matches.
- Preserve the existing manual approve/remove evidence flow.
- Include candidate fit brief context in evidence matching input where useful.
- Add an AI provider method for application strategy generation.
- Application strategy input should include job analysis, candidate fit brief, approved evidence, evidence quality, unmatched requirements, gap decisions, approved custom facts, selected language, and tone preference.
- Application strategy output should include primary angles, secondary angles, gap handling guidance, avoid claims, tone guidance, and draft outline.
- Strategy angles must reference approved evidence ids when they support concrete claims. They may reference profile fact ids only for narrative context traceability.
- Weak evidence should not support direct experience claims. If kept, it should guide cautious wording or prompt the user to add stronger evidence/custom facts.
- Strategy generation should run only after the user has reviewed evidence and gap decisions, immediately before draft generation or as part of the guided draft action. It must not run during `Prepare application`.
- Persist `ApplicationStrategy` as latest application workflow state.
- Record an `AiRun` step for `ApplicationStrategy`.
- Show a compact strategy summary near draft review or before generation. Keep frontend changes compact: quality labels, weak-match affordances, and strategy summaries only; no editable strategy or complex new review screens in V2.2.

## Testing Decisions

- Cover evidence matching validation for `Strong`, `Partial`, `Weak`, and invalid quality values.
- Cover unsupported signals becoming unmatched requirements.
- Cover weak evidence being opt-in only and not preselected, auto-approved, or visually equal to strong/partial evidence.
- Cover evidence matching avoiding duplicate/conflicting signal handling as before.
- Cover application strategy generation running only after evidence and gap review, not during preparation.
- Cover application strategy generation using candidate fit brief and approved evidence.
- Cover strategy angles requiring approved evidence ids for concrete claim support, with profile fact ids allowed only for narrative context.
- Cover strategy validation for missing arrays, invalid evidence ids, and invalid profile fact ids.
- Cover gap decisions flowing into strategy generation.
- Cover provider failure preserving the prior stable draft and preparation state.
- Cover fake provider deterministic evidence quality and application strategy output.
- Cover frontend quality labels and weak-match review behavior where existing test seams support it.

## Out of Scope

- Final draft prompt rewrite beyond passing strategy through contracts.
- Claim audit changes.
- Editable strategy.
- Complex new evidence or strategy review screens.
- Automatic evidence approval.
- New profile import flows.
- Full workflow history.
- Provider/model selection UI.
- Export changes.

## Further Notes

This milestone should make the trust checkpoint smarter. The user should no longer see a flat list of matches that all look equally credible. The app should help separate strong proof from cautious context, then turn that reviewed evidence into a deliberate writing plan.
