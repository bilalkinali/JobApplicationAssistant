# V2.2 Milestone 3 Product Requirements Document

Status: draft
Source: docs/planning/v2/v2.2-creative-application-generation-spec.md

## Goal

Rewrite draft generation and audit behavior so the app produces creative, specific, human application text from the candidate fit brief and application strategy while preserving claim safety.

## Problem Statement

After the app has richer candidate context, evidence quality, and a strategy, the final draft prompt still needs to stop behaving like a legal checklist. The generated output should not simply repeat accepted skills or mirror job-posting phrases. It should synthesize the candidate's strongest relevant story angles into a natural cover letter and a distinct short motivation.

At the same time, the app must keep its trust promise: concrete claims need support, gaps must not become fake experience, and edits must be auditable.

## Solution

Milestone 3 revises draft generation to use the `CandidateFitBrief`, `ApplicationStrategy`, approved evidence, approved custom facts, and gap decisions. Draft generation should not receive raw full approved profile facts unless a specific implementation need requires them. The preferred proof path is approved evidence and approved custom facts; the preferred narrative path is the fit brief and strategy.

The draft prompt should ask for natural, persuasive writing in the selected language, based on 2-3 chosen story angles. It should treat the fit brief as writing context and per-application approved evidence as proof context. The short motivation should become a concise value proposition rather than a compressed duplicate of the cover letter.

Claim audit should be updated to understand the new context shape. It should still mark unsupported concrete claims, but it should distinguish cautious motivation or learning-interest statements from claims of experience. It must explicitly fail concrete claims that are supported only by `CandidateFitBrief.profileFactIds` and not by approved evidence or approved job-local custom facts.

## User Stories

1. As a job applicant, I want the generated cover letter to feel tailored and human, so that it is useful as a first draft.
2. As a job applicant, I want the draft to use my broader background, so that it can mention relevant education, projects, business experience, communication, location, and technical strengths where supported.
3. As a job applicant, I want the letter to focus on the strongest story angles, so that it does not read like a list of requirements.
4. As a job applicant, I want the draft to avoid copying large phrases from the job posting, so that it sounds like me.
5. As a job applicant, I want repeated evidence to be used carefully, so that one project does not dominate every paragraph unless it truly should.
6. As a job applicant, I want transferable competencies included when supported, so that the app can use more than tool names.
7. As a job applicant, I want gaps to be mentioned only according to my decisions, so that the draft stays honest.
8. As a job applicant, I want the short motivation to be a distinct pitch, so that it is useful in forms and not just a summary.
9. As a job applicant, I want unsupported claims to remain visible in claim audit, so that creativity does not weaken trust.
10. As a job applicant, I want broad soft-skill claims audited against supporting evidence, so that the draft does not become generic.
11. As a developer, I want draft generation input to include strategy and fit brief, so that final prose is based on structured intermediate context.
12. As a developer, I want claim audit to validate claims against approved evidence, approved custom facts, fit brief support mappings, and gap decisions, so that the safety net matches the new pipeline.
13. As a developer, I want manual QA to compare app output with a direct-chat baseline using the same model, so that V2.2 quality is tested against the actual product complaint.

## Implementation Decisions

- Revise `draft-generation.md` to use strategy-led writing rather than exhaustive evidence listing.
- Draft generation input should include candidate fit brief, application strategy, approved evidence, approved custom facts, unmatched requirements, and gap decisions.
- Draft generation should not receive the raw full set of approved profile facts unless strictly needed for a documented edge case. Prefer `CandidateFitBrief`, `ApplicationStrategy`, approved evidence, and approved custom facts so generation cannot bypass evidence review.
- Treat candidate fit brief as writing context only; concrete claims still need per-application approved evidence or approved job-local custom facts.
- Use approved evidence and approved custom facts as proof context.
- Do not treat fit brief profile fact ids as direct proof unless that profile fact has also been selected into approved evidence for the current application.
- Tell the model to choose 2-3 coherent story angles and avoid covering every requirement.
- Tell the model to avoid large phrase copying from the job posting.
- Tell the model to avoid generic interest statements unless grounded in concrete reasons.
- Tell the model to avoid repeating one profile fact across unrelated claims.
- Tell the model to write the short motivation as a distinct concise value proposition.
- Revise `claim-audit.md` so it understands strategy/fit brief support mappings, cautious learning-interest wording, and broad competency claims.
- Claim audit must fail concrete claims supported only by `CandidateFitBrief.profileFactIds`. Passing support requires approved evidence or approved job-local custom facts.
- Claim audit should keep using strict JSON validation and existing stale-audit behavior.
- Preserve the combined generate-and-audit guided action.
- Preserve existing export behavior.
- Add manual QA notes/checklist for comparing V2.2 output to a direct-chat baseline.

## Testing Decisions

- Cover draft generation receiving candidate fit brief and application strategy without the raw full approved profile fact set unless strictly needed.
- Cover draft generation excluding unapproved custom facts and unapproved imported profile facts.
- Cover `MentionAsLearningInterest` producing cautious wording only.
- Cover ignored gaps not being emphasized unless independently supported.
- Cover generated short motivation being non-empty and distinct from cover letter text.
- Cover claim audit marking unsupported concrete claims as unsupported.
- Cover claim audit treating cautious motivation/interest statements differently from experience claims.
- Cover claim audit rejecting concrete claims that are supported only by fit brief profile fact ids but not by approved evidence or approved job-local custom facts.
- Cover manual edits still marking audit stale.
- Cover fake provider deterministic strategy-led draft output.
- Add or update manual QA documentation for the Vejle Kommune AI-builder scenario.

## Out of Scope

- New export formats.
- DOCX template redesign.
- Editable strategy.
- Automatic job submission.
- Provider/model selection changes.
- Full draft version history.
- Full profile fact revision history.
- New frontend design beyond compactly showing fit brief, quality labels, strategy summaries, and audit context.
- Editable strategy or complex new review screens.

## Further Notes

This is the quality milestone. Success is not just that the JSON validates or the draft exists. Success is that the Vejle Kommune AI-builder example produces text that uses the candidate's broader background: local AI tooling, integrations, education, business/customer experience, communication, technical architecture, language/location fit, and honest learning interest where relevant.

The app should feel closer to the successful direct-chat workflow, but with the product's evidence approval and audit safety rails intact.
